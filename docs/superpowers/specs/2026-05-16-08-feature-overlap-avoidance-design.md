# 08. 機能重複の回避（bookmee の境界）

改善案: ⑧ 既存ソフトとの機能重複は避ける

## 背景
- 牧野氏: 「freee/MF側ですでに見れるものをここでも見せても、結局そっち直で見に行けなくない？」
- OCR・自動仕訳のコア部分は freee/MF に任せ、bookmee はその上の**レビュー・タスク管理・横串連絡**層に集中する。
- これは01（クロスベンダー集約）とセットで「bookmeeは何をするツールか」を定義する境界線。

## 性質
これは**横断指針**。単独機能ではなく、各機能の実装PRでこの境界に違反していないかをレビュー観点とする。

## 本番アーキとの関係
- MF は実API連携（取得のみ、書き込みなし）
- freee は `freee-mock.ts` で固定データ提供
- bookmee 内では「読み取り＋ジャンプリンク」のみ。**生データの編集UIは作らない**
- 同期遅延を全画面で明示

## bookmee の境界（Yes / No 定義）

### bookmee が持つもの（YES）

| 機能 | 理由 |
|---|---|
| 顧問先横断のレビューキュー | freee/MF は単一テナント前提。横串はサードパーティの強み |
| ベンダーをまたいだ集約ビュー | freee/MF 単独では実現不可能 |
| スタッフ→税理士の承認ワークフロー | 既存ソフトに無い盲点（02） |
| 顧問先別のリスクルール蓄積 | freee/MF の自動仕訳より上のレイヤー（04） |
| 顧問先別の連絡チャンネル管理＋実送信 | 既存ソフト外の領域（03） |
| 不足証憑の検出と依頼文生成 | freee/MFは「ある証憑を紐付ける」までで止まる（07） |
| 月次/期末モードの切替と画面分岐 | freee/MFは画面分けの概念無し（05） |
| 事務所運営の進捗ダッシュボード | 顧問先全体の俯瞰は既存ソフトの範囲外 |

### bookmee が持たないもの（NO）

| 機能 | 任せ先 | 理由 |
|---|---|---|
| OCR / 自動仕訳の生成 | freee / MF | 既に高品質 |
| 仕訳の直接編集 | freee / MF | 入力UIは元ソフトが正規 |
| 銀行明細の取得 | freee / MF | API経由で取得済の数字を読むのみ |
| 請求書発行 | freee / MF | 別領域 |
| 給与計算 | freee 人事労務 / MF クラウド給与 | 別プロダクト |
| 申告書出力 | freee 申告 / 弥生 / etc. | 別プロダクト |
| 帳票の生成 (試算表PDF等) | freee / MF | 出力は元ソフトでDL |
| 口座残高の本物の照合 | freee / MF | 同期した値を表示するのみ |
| 受信メッセージの取り込み | 既存メーラー / Slack等 | bookmeeは送信のみ |

## 設計原則

### O1. 「ジャンプ」ファーストUI
bookmee 内で生データを再現する代わりに、必ず**freee/MFの該当画面を開くリンクボタン**を併設する。

実装:
- `renderTable()` の各行末に「freeeで開く」「MFで開く」ボタン
- 押下で `window.open(row.deepLink)`（サーバが `buildVendorDeepLink()` で生成）
- 01 の F6 と統合

### O2. データを「読み取り専用」で扱う
bookmee の画面で freee/MF 由来データを編集できる UI を作らない。
- 仕訳の摘要・金額・科目変更フォームは作らない
- 「修正は freee で行ってください」リンクへ誘導
- API 側でも `Entry` `Receipt` `Matching` への PATCH/DELETE エンドポイントを公開しない

例外（bookmee 固有データなので編集可）:
- `Rule`, `Task.stage`, `Task.history`, `Thread`, `ReceiptPolicy`, `Client.mode`, `Client.contactEndpoints`

### O3. 同期遅延の明示
freee/MF 由来データには必ず「最終同期: 2026-05-15 08:30」を添える。
- `renderTable()` のテーブル下に `renderSyncFreshness(syncObj)` を表示
- 古いデータでの判断ミスを避ける

### O4. 重複機能を作りそうになったら
PR レビュー時のチェックリスト:
- [ ] このUIは freee/MF が既に提供している画面の再実装ではないか？
- [ ] もし「同等の機能」を作っているなら、それは横串・承認・連絡のいずれかの軸を持っているか？
- [ ] 「とりあえず見せる」ためだけのUIになっていないか？

該当するならスコープから外す。

## 既存スペックへの影響

### 01 への補強
- F6（生データへのジャンプリンク）は本指針の具体実装
- ベンダーバッジ、出所列も本指針の表れ
- freee は `freee-mock.ts` で実装し、MF と同じ adapter インターフェースに揃える

### 03 への補強
- メール本文・Slack文を bookmee 内で「下書き」するが、**送信実体は外部チャンネル**に任せる
- ただし「送信」自体は実装する（実送信API）
- 受信メッセージのリッチ表示はしない（preview のみ）

### 07 への補強
- 不足証憑の「手動添付」UIは作らない
- 「freee/MF の証憑画面を開く」ボタンに置き換え

## 実装上の具体タスク

| 対象 | アクション |
|---|---|
| `renderTable` | 各行末に vendor ジャンプボタンを追加（01 F6 と一致） |
| `renderReceipts` | 「証憑を手動添付」ボタンを「freee/MFで証憑を見る」に置換 |
| `renderTrends` | 試算表の数字表示は維持。「詳細はfreeeで」リンクを追加 |
| 新規 `buildVendorDeepLink(row, vendor)` (server) | モックURLを返す純関数。MFは公式仕様に追従、freeeはプレースホルダ |
| 新規 `renderSyncFreshness(syncObj)` (client) | 「最終同期: ...」表示を統一 |
| 全 API ルート | Entry/Receipt/Matching への書き込みエンドポイントは作らない（read-only） |
| 全 `render*` | 編集UIは原則禁止。違反箇所は読取り専用に変更 |

## styles.css 追加
- `.vendor-link { font-size:11px; color:#0e8be5; text-decoration:underline; cursor:pointer }`
- `.sync-fresh { font-size:11px; color:#5c6675 }`
- `.read-only-note { font-size:11px; color:#8a2035 }` （編集不可表示用）

## スコープ外
- 実ディープリンク仕様（OAuth、画面ID）の確定
- freee 実API連携（モック維持）
- 同期ジョブの設計詳細（09 で扱う）

## 受入基準（横断レビュー観点）
- [ ] 仕訳・証憑・消込・試算表テーブルの各行から freee/MF の該当画面を開くボタンがある
- [ ] bookmee 内で仕訳・摘要・金額の編集UIが存在しない
- [ ] API 側で Entry/Receipt/Matching への書き込みエンドポイントが公開されていない
- [ ] freee/MF 由来データの近くに必ず「最終同期: …」が表示される
- [ ] freee は `freee-mock.ts` の固定データ、MF は実API、両者が同じ adapter インターフェースを実装
- [ ] 各機能スペック（01〜07, 09）の実装PRが、本指針 O1〜O4 を満たすことが確認される
